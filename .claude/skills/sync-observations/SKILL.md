# Sync observations

Reproduce, as a repeatable skill, the author's own three-step habit: notice a
new fact in a `breakout/*.md` map/data write-up's `## Observations` section,
record it in `prompt/tree-prompt.yaml`'s `obervation-list` (keep that exact
spelling — it is a pre-existing key, not a typo to fix), and refresh the
corresponding row of the `# Personal Thoughts` table in `README.md` so the
three stay in sync.

Arguments (`$ARGUMENTS`, optional): one or more `breakout/*.md` file paths to
check. If omitted, scan every `breakout/*.md` file except `combined.md`
(the evidence-diagram output — not a map/data source breakout).

## Scope — what this skill touches, and what it doesn't

- **In scope:** each breakout file's `## Observations` section only. These
  are the neutral map/data notes the author "notices" — e.g. a road's path,
  a washout, a parcel name on a cadastre.
- **Out of scope:** a breakout file's own `## Personal Thoughts` section
  (the author's inferences about *that* file — a different, file-local
  thing from the README's `# Personal Thoughts` table), and
  `prompt/tree-prompt.yaml`'s `personal-musings` field. Neither is read or
  written by this skill. (`/locate-tree-and-spring` is the skill that
  consumes `personal-musings`; suggest running it afterward per step 7, but
  don't do its job here.)
- `combined.md` is never scanned — it is generated by `/evidence-diagram`,
  not an observation source.

## What to read, every time

1. Every in-scope `breakout/*.md` file's `## Observations` bullet list
   (some files, like `copernicus.md`, have no such section — skip them).
2. `prompt/tree-prompt.yaml`'s `obervation-list` array (each entry has a
   `source` key and a `remarks` list).
3. `README.md`'s `# Personal Thoughts` table (one row per breakout file,
   second column a prose paragraph, not bullets).

## Rules

1. **Additive only.** Never delete or reword an existing `obervation-list`
   remark or an existing README table row's content — only add. If a bullet
   the author trimmed out of the yaml by hand is still sitting in a
   breakout file, that was very likely a deliberate edit, not an oversight;
   rule 2 is what keeps this skill from blindly re-adding it.
2. **A bullet counts as "already synced" if it (or an evident paraphrase of
   it) appears in *either* the yaml's `obervation-list` *or* the README
   table** — not only the yaml. Only bullets missing from *both* are
   genuinely new. (Precedent: "The ridge road could have been more to the
   west than the current D53" was hand-removed from the yaml's `Carte de
   L'etat major 1820-1866` entry but is still in the README table and in
   `carte-etat-major.md` itself — treat that as already handled, not as
   something to re-add.)
3. **Matching a bullet to a `source` key is a judgment call — follow this
   order, and say which one applied:**
   a. If the bullet text itself carries an explicit `"<Name>:"` prefix (as
      every bullet in `carte-etat-major.md` does — `"Lidar Scan: ..."`,
      `"Carte de L'etat major 1820-1866: ..."`), use that literal name as
      the `source` key (matching an existing key case-insensitively if one
      already exists), and strip the prefix before storing the remark text
      — the yaml's remarks never repeat the source name inside the text.
   b. Otherwise, check precedent: has this breakout file's un-prefixed
      bullets previously landed under a specific existing `source` key? (E.g.
      `napoleonic.md`'s un-prefixed bullets live under the `Carte de L'etat
      major 1820-1866` key, not a `napoleonic-cadastre` key — the author's
      own prior choice, not a filename-derived default.) Follow established
      precedent over inventing a new key.
   c. Otherwise (no prefix, no precedent — e.g. a brand-new breakout file),
      default to a new `source` key derived from the file's own title/name,
      and flag this as a judgment call for the user to confirm rather than
      silently deciding — a future run may reveal the author actually wanted
      it merged into an existing key, as happened with `napoleonic.md`.
4. **Never fabricate a remark.** Only carry over text that is actually a
   bullet under a breakout file's `## Observations` heading — not its
   `## Personal Thoughts` bullets, not prose from the "What Claude Code
   thinks of it" section if one exists.
5. **README row rebuild is a full refresh of that row's cell, not an
   append.** Once a `source` key's remarks list gains a new entry, rebuild
   the whole second-column paragraph for every breakout file mapped to that
   key, by joining the *complete current* remarks list for that key into
   sentences in the same prose style already used in the table (period-
   separated, no bullet markers) — don't just tack the new sentence onto the
   old paragraph, since wording may need to flow together. Leave every
   other row untouched. Keep the first column's `[name](breakout/file.md)`
   link exactly as it already appears.

## Steps

1. Read every in-scope breakout file (or just the ones named in
   `$ARGUMENTS`) and pull out its `## Observations` bullets, if any.
2. Read `prompt/tree-prompt.yaml`'s `obervation-list` and flatten all
   `remarks` across all `source` entries into one lookup list.
3. Read `README.md`'s `# Personal Thoughts` table.
4. For each breakout file's Observations bullets, drop any that are already
   synced per rule 2. What's left is genuinely new.
5. For each new bullet, resolve its `source` key per rule 3, stripping any
   `"<Name>:"` prefix from the stored text.
6. Edit `prompt/tree-prompt.yaml`: append each new remark to its resolved
   `source` entry's `remarks` list (creating a new `source` entry only when
   rule 3c applies), preserving existing entries, order, and indentation
   exactly.
7. For every `source` key that changed, rebuild the affected README row(s)
   per rule 5, and edit `README.md` in place.
8. Report to the user exactly what changed: which breakout file(s) had new
   bullets, which `source` key each landed under (naming which part of rule
   3 decided it, and flagging any 3c judgment call explicitly), and which
   README row(s) were rebuilt. If nothing was new, say so plainly rather
   than padding the report.
9. Suggest — don't run automatically — `/locate-tree-and-spring`, since a
   newly added observation can change the best-guess geolocation for the
   tree or spring.

## Output

Edits to two files: `prompt/tree-prompt.yaml` (new remarks appended to the
right `obervation-list` source entries) and `README.md` (the affected
`# Personal Thoughts` row(s) rebuilt from the complete, current remarks for
that source). No new files are created. Nothing is deleted. When a bullet's
`source` key can't be resolved mechanically (rule 3c), say so and propose a
default rather than deciding silently.
