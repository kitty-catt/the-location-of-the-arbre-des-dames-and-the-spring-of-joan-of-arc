# Sync observations

Reproduce, as a repeatable skill, the author's own habit: notice a new fact
or inference in a `breakout/*.md` map/data write-up, record it in
`prompt/tree-prompt.yaml` (keeping the pre-existing `obervation-list`
spelling — not a typo to fix), and keep the `# Personal Thoughts` table in
`README.md` in sync. This skill handles **two independent jobs**, each with
its own source of truth:

| Job | Reads from | Writes to |
|---|---|---|
| Sync new bullets into the yaml | each breakout file's `## Observations` / `Personal Thoughts` bullets, diffed against the yaml | `prompt/tree-prompt.yaml` (`obervation-list` grouped by `source`; `personal-musings` flat) |
| Rebuild the README table | **every** breakout file's `## Observations` / `Personal Thoughts` bullets, directly, every run | `README.md`'s `# Personal Thoughts` table, entirely |

The table is **not** patched incrementally and does **not** mirror the yaml
— it is thrown away and rebuilt from the breakout files every time this
skill runs. (Earlier versions of this skill patched only the row/cell that
seemed to have changed, which let the `naudin-map` row silently go stale —
missing its first remark for a whole run. Full rebuild makes that bug
structurally impossible: there is no stale state to carry forward.)

Arguments (`$ARGUMENTS`, optional): one or more `breakout/*.md` file paths to
check. If omitted, scan every `breakout/*.md` file except `combined.md`
(the evidence-diagram output — not a map/data source breakout).

## Scope

- **In scope:** each breakout file's `## Observations` section (neutral
  map/data notes — a road's path, a washout, a parcel name on a cadastre)
  **and** its `Personal Thoughts` section (the author's own inferences about
  *that* file). Heading level for "Personal Thoughts" is inconsistent across
  files — some use `#`, `napoleonic.md` uses `##` — match on the heading
  *text*, not its depth.
- **Out of scope:** a breakout file's "What Claude Code thinks of it"
  section, if present (that's AI commentary, not an author observation or
  musing — never carry it over, in either job).
- `combined.md` is never scanned — it is generated by `/evidence-diagram`,
  not an observation/musing source.
- This skill does not touch `first-hand-snippets`, `candidate-locations`, or
  `object-model`. `/locate-tree-and-spring` is the skill that *consumes*
  `personal-musings` and `obervation-list` to re-derive a geolocation;
  suggest running it afterward per the last step, but don't do its job here.

## What to read, every time

1. Every in-scope breakout file's `## Observations` bullets and
   `Personal Thoughts` bullets (either may be absent or empty — e.g.
   `copernicus.md` has neither section at all; `naudin.md`'s `Personal
   Thoughts` heading currently has no bullets under it).
2. `prompt/tree-prompt.yaml`'s `obervation-list` array (each entry has a
   `source` key and a `remarks` list) and its `personal-musings` array (a
   flat list of strings — no per-source grouping). Needed for the yaml-sync
   job only.
3. `README.md`'s current `# Personal Thoughts` table — not to diff against,
   but to preserve each existing row's exact `[display-name](path)` link
   text and row order when rebuilding (see rule 4).

## Rules — yaml-sync job (additive only)

1. **Additive only.** Never delete or reword an existing `obervation-list`
   remark or `personal-musings` entry — only add. A bullet counts as
   "already synced" if it (or an evident paraphrase) is already present in
   its yaml destination (`obervation-list` for Observations,
   `personal-musings` for Personal Thoughts) — check the yaml only; the
   README table is a derived view now (see the rebuild job below), not an
   independent record, so it is no longer a dedup signal.
2. **Resolving an Observations bullet's `source` key:**
   a. An explicit `"<Name>:"` prefix in the bullet (as in
      `carte-etat-major.md`) names the `source` key directly (match an
      existing key case-insensitively; strip the prefix before storing).
   b. Otherwise, follow precedent: has this breakout file's un-prefixed
      bullets previously landed under a specific existing `source` key?
      (E.g. `napoleonic.md`'s un-prefixed Observations live under `Carte de
      L'etat major 1820-1866`, not a `napoleonic-cadastre` key of their
      own.) Precedent beats a filename-derived default.
   c. Otherwise, default to a new `source` key derived from the file's own
      title/name, and flag it as a judgment call for the user to confirm.
3. **`personal-musings` entries carry no key.** Append new `Personal
   Thoughts` bullets as plain strings, verbatim, in the order encountered —
   no grouping, no attribution field, matching the existing entries' style.
4. **Never fabricate.** Only carry over text that is actually a bullet under
   a breakout file's `## Observations` or `Personal Thoughts` heading.

## Rules — README table rebuild job (full regeneration)

5. **Every run regenerates the whole table, unconditionally** — all rows,
   both content columns — directly from each in-scope breakout file's
   current `## Observations` and `Personal Thoughts` bullets. Never reuse
   or patch the table's previous content; never read it as a source of
   bullets. Strip any `"<Name>:"` prefix from an Observations bullet before
   putting it in the table (the prefix is yaml bookkeeping, not prose).
6. **Render each cell as a bullet list, not joined prose.** A bare `-`
   markdown list doesn't render inside a single-line GFM table cell, so use
   an HTML list: `<ul><li>First bullet</li><li>Second bullet</li></ul>`, one
   `<li>` per bullet, in the breakout file's own order. Keep each bullet's
   wording verbatim (aside from stripping a `"<Name>:"` prefix per rule 5) —
   don't merge bullets into sentences or add connecting words. Use a plain
   `-` (no list) for a cell whose section is absent or empty (e.g.
   `naudin-map`'s Personal Thoughts cell, `copernicus-map`'s both cells).
7. **Preserve each row's identity, not its content.** Keep the existing
   `[display-name](breakout/file.md)` link text and the existing row order
   for every breakout file already in the table — these names aren't purely
   mechanical (`napoleonic.md` → `napoleonic-cadastre`, not
   `napoleonic-map`), so don't re-derive them. Only for a breakout file with
   no existing row (a brand-new file), add one at the end with a sensible
   derived display name, and flag that choice for the user to confirm.

## Steps

1. Read every in-scope breakout file (or just the ones named in
   `$ARGUMENTS`) and pull out its `## Observations` bullets and its
   `Personal Thoughts` bullets, if any.
2. **Yaml-sync job:** read `prompt/tree-prompt.yaml`'s `obervation-list`
   (flatten all `remarks`) and `personal-musings`. Drop any breakout bullet
   already present per rule 1. For what's left, resolve each Observations
   bullet's `source` key (rule 2) and append it; append each new Personal
   Thoughts bullet to `personal-musings` (rule 3) — preserving all existing
   entries, order, and indentation exactly.
3. **Table-rebuild job**, independent of step 2's results: for every
   in-scope breakout file, build its row's two content cells fresh from
   that file's *current* Observations and Personal Thoughts bullets (rules
   5–6), reusing each existing row's display name/link and order (rule 7).
   Replace the entire table in `README.md` with the result.
4. Report to the user: for the yaml-sync job, exactly what was newly added
   and where (which `source` key / rule each Observations bullet landed
   under, which Personal Thoughts bullets joined `personal-musings`) — say
   so plainly if nothing was new. For the table rebuild, note it happened
   unconditionally, and call out specifically if any row's content actually
   changed versus what was there before (so the user can see the effect of
   a full rebuild, not just that one occurred).
5. Suggest — don't run automatically — `/locate-tree-and-spring`, since a
   newly added observation or musing can change the best-guess geolocation
   for the tree or spring.

## Output

Edits to two files: `prompt/tree-prompt.yaml` (new remarks appended to the
right `obervation-list` source entries, new bullets appended to
`personal-musings` — additive only, nothing removed) and `README.md` (the
entire `# Personal Thoughts` table replaced with a fresh rebuild straight
from the breakout files, each cell an HTML bullet list (`<ul><li>...</li></ul>`)
of that file's own bullets rather than joined prose — including rows that
didn't change, since the rebuild is unconditional). No new files are
created. When an Observations
bullet's `source` key can't be resolved mechanically (rule 2c) or a brand-new
breakout file needs a new row (rule 7), say so and propose a default rather
than deciding silently.
