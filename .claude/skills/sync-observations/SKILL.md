# Sync observations

Reproduce, as a repeatable skill, the author's own habit: notice a new fact
or inference in a `breakout/*.md` map/data write-up, record it in
`prompt/tree-prompt.yaml` (keeping the pre-existing `obervation-list`
spelling — not a typo to fix), and refresh the matching row of the
`# Personal Thoughts` table in `README.md` so all three stay in sync. This
skill handles **both** halves of a breakout file in parallel:

| Breakout file section       | yaml destination   | README column        |
|------------------------------|---------------------|-----------------------|
| `## Observations`            | `obervation-list` (grouped by `source`) | "Observations" (2nd column) |
| `# Personal Thoughts` / `## Personal Thoughts` | `personal-musings` (flat list) | "Personal Thoughts" (3rd column) |

Arguments (`$ARGUMENTS`, optional): one or more `breakout/*.md` file paths to
check. If omitted, scan every `breakout/*.md` file except `combined.md`
(the evidence-diagram output — not a map/data source breakout).

## Scope

- **In scope:** each breakout file's `## Observations` section (neutral
  map/data notes — a road's path, a washout, a parcel name on a cadastre)
  **and** its `Personal Thoughts` section (the author's own inferences about
  *that* file). Heading level for "Personal Thoughts" is inconsistent across
  files — some use `#`, `napoleonic.md` uses `##` — match on the heading
  *text*, not its depth.
- **Out of scope:** a breakout file's "What Claude Code thinks of it"
  section, if present (that's AI commentary, not an author observation or
  musing — never carry it over).
- `combined.md` is never scanned — it is generated by `/evidence-diagram`,
  not an observation/musing source.
- This skill does not touch `first-hand-snippets`, `candidate-locations`, or
  `object-model`. `/locate-tree-and-spring` is the skill that *consumes*
  `personal-musings` and `obervation-list` to re-derive a geolocation;
  suggest running it afterward per the last step, but don't do its job here.

## What to read, every time

1. Every in-scope breakout file's `## Observations` bullets and
   `Personal Thoughts` bullets (either may be absent or empty — e.g.
   `copernicus.md` has neither section at all; `naudin.md`'s `Personal
   Thoughts` heading currently has no bullets under it).
2. `prompt/tree-prompt.yaml`'s `obervation-list` array (each entry has a
   `source` key and a `remarks` list) and its `personal-musings` array (a
   flat list of strings — no per-source grouping).
3. `README.md`'s `# Personal Thoughts` table — two content columns,
   "Observations" and "Personal Thoughts" (plus the object/link column).

## Rules

1. **Additive only, both yaml arrays.** Never delete or reword an existing
   `obervation-list` remark, an existing `personal-musings` entry, or any
   existing README cell content — only add. A bullet the author trimmed out
   of the yaml by hand was very likely a deliberate edit, not an oversight;
   rule 2 is what stops this skill from blindly re-adding it.
2. **A bullet counts as "already synced" if it (or an evident paraphrase)
   appears in *either* its yaml destination *or* the matching README
   column** — not only the yaml. Only bullets missing from *both* are
   genuinely new. (Precedent: "The ridge road could have been more to the
   west than the current D53" was hand-removed from the yaml's `Carte de
   L'etat major 1820-1866` `obervation-list` entry but is still in the
   README's Observations column and in `carte-etat-major.md` itself — treat
   that as already handled. The same text also now appears as a `Personal
   Thoughts` bullet in `napoleonic.md`; check it against `personal-musings`
   and the README's Personal Thoughts column independently of its
   Observations-side history — the two tracks don't share dedup state.)
3. **Resolving an Observations bullet's `source` key** (unchanged from
   before — `personal-musings` has no analogous key, see rule 4):
   a. An explicit `"<Name>:"` prefix in the bullet (as in
      `carte-etat-major.md`) names the `source` key directly (match an
      existing key case-insensitively; strip the prefix before storing).
   b. Otherwise, follow precedent: has this breakout file's un-prefixed
      bullets previously landed under a specific existing `source` key?
      (E.g. `napoleonic.md`'s un-prefixed Observations live under `Carte de
      L'etat major 1820-1866`, not a `napoleonic-cadastre` key of their
      own.) Precedent beats a filename-derived default.
   c. Otherwise, default to a new `source` key derived from the file's own
      title/name, and flag it as a judgment call for the user to confirm.
4. **`personal-musings` entries carry no key.** Append new `Personal
   Thoughts` bullets to `personal-musings` as plain strings, verbatim, in
   the order encountered — no grouping, no attribution field, matching the
   existing entries' own style.
5. **Never fabricate.** Only carry over text that is actually a bullet under
   a breakout file's `## Observations` or `Personal Thoughts` heading —
   never prose from "What Claude Code thinks of it", and never a bullet
   from one section miscounted as the other.
6. **Each README cell rebuild is a full refresh, not an append.** Once a
   `source` key's remarks (Observations column) or the overall
   `personal-musings` list (Personal Thoughts column) gains a new entry for
   a given breakout file, rebuild that *whole cell* by joining the complete
   current set of relevant bullets into sentences in the same prose style
   already used in the table (period-separated, no bullet markers) — don't
   just tack the new sentence onto old prose. The two columns are rebuilt
   independently: a change to one does not require touching the other.
   Leave every other row, and the untouched column of a changed row, as-is.
   Keep the first column's `[name](breakout/file.md)` link exactly as it
   appears. Use `-` for a cell with no bullets, matching the existing
   convention (e.g. `copernicus-map`'s Observations cell).

## Steps

1. Read every in-scope breakout file (or just the ones named in
   `$ARGUMENTS`) and pull out its `## Observations` bullets and its
   `Personal Thoughts` bullets, if any.
2. Read `prompt/tree-prompt.yaml`'s `obervation-list` (flatten all `remarks`
   across all `source` entries into one lookup list) and its
   `personal-musings` array.
3. Read `README.md`'s `# Personal Thoughts` table, both content columns.
4. For each breakout file's Observations bullets, drop any already synced
   per rule 2 against `obervation-list`/README Observations column. For
   each file's Personal Thoughts bullets, separately drop any already
   synced per rule 2 against `personal-musings`/README Personal Thoughts
   column. What's left in each track is genuinely new.
5. For each new Observations bullet, resolve its `source` key per rule 3,
   stripping any `"<Name>:"` prefix. New Personal Thoughts bullets need no
   key resolution (rule 4).
6. Edit `prompt/tree-prompt.yaml`: append new Observations remarks to their
   resolved `source` entries (creating a new entry only under rule 3c), and
   append new Personal Thoughts bullets to `personal-musings` — preserving
   all existing entries, order, and indentation exactly.
7. For every breakout file whose Observations or Personal Thoughts changed,
   rebuild the corresponding README cell(s) per rule 6, and edit `README.md`
   in place. If the table currently has only two columns (object + a single
   "Observations" column), add the "Personal Thoughts" header and a third
   cell per row before filling it in — do this once, non-destructively, and
   say so in the report.
8. Report to the user exactly what changed: which breakout file(s) had new
   Observations bullets (and which `source` key / rule each landed under),
   which had new Personal Thoughts bullets (now in `personal-musings`), and
   which README cells were rebuilt. If nothing was new in either track, say
   so plainly rather than padding the report.
9. Suggest — don't run automatically — `/locate-tree-and-spring`, since a
   newly added observation or musing can change the best-guess geolocation
   for the tree or spring.

## Output

Edits to two files: `prompt/tree-prompt.yaml` (new remarks appended to the
right `obervation-list` source entries, new bullets appended to
`personal-musings`) and `README.md` (the affected Observations and/or
Personal Thoughts cell(s) rebuilt from the complete, current source
material, with a third column added to the table if it isn't there yet).
No new files are created. Nothing is deleted. When an Observations bullet's
`source` key can't be resolved mechanically (rule 3c), say so and propose a
default rather than deciding silently.
